# Phase 0 GIS release workflow

Phase 0.5-E adds the operator-only [immutable object delivery workflow](../docs/operations/spatial-object-publication.md). Use `publish-object-release.ts` for already approved registered terrain/road outputs; it does not replace GIS QA, invent source rights, or mutate an existing published release. Cloud runtime derives URLs from its approved public origin and PostGIS delivery receipt, without web deployment disk assets.

Run from the LAND monorepo using Node 24 and a dedicated Python environment with `pip install -r pipelines/requirements.txt`. No BIKER/TRIP database, provider credentials or terrain secrets are used.

1. `node pipelines/acquire.mjs` downloads the Copernicus GLO-30 COG N21 E104 and NGA EGM2008 geoid grid. First acquisition records public URLs, bytes, download time and SHA-256 in `sources.lock.json`; later runs require identical bytes. Review a changed upstream input as a new source version.
2. `python pipelines/terrain.py` requires the pinned hashes. It clips/reprojects with GDAL through Rasterio to EPSG:32648 at 60 m, uses an explicit PROJ vertical grid shift with multiplier +1 (`h = H + N`), then samples a bounded WGS84 geographic hierarchy. Missing grid/NoData/nonfinite values fail. No guessed vertical offset or coordinate swapping is allowed.
3. `python pipelines/verify_terrain.py` reads all 341 released tile files, verifies every checksum and checks identical shared edges. The build also checks horizontal/vertical round trips and independently samples the geoid raster. Those are numerical processing checks; field control points and local absolute accuracy remain UNKNOWN.
4. `node pipelines/acquire-roads.mjs` acquires one bounded Overpass snapshot and pins the query, OSM timestamp and hash in `roads.lock.json`. It performs no automatic retry and is not called by the website. For recurring commercial acquisition use a suitable extract/provider rather than depending on a volunteer endpoint.
5. `python pipelines/roads.py` clips valid OSM LineStrings to the operational AOI, keeps allowlisted names/source IDs/classes and UNKNOWN verification. It never infers access, surface condition or safety. The resulting extract contains 208 segments.
6. `node --env-file=.env.local pipelines/register-local-release.mjs` promotes already processed releases for **local QA** to ignored `apps/web/public/spatial/<kind>/<version>/`. It checks LAND database identity, source rights and entry/tile hashes, registers source/dataset/assets/pipeline/audit, and verifies road geometry in PostGIS. Existing public URLs must have identical bytes. Local technical QA publication does not verify source facts or imply production deployment approval.

The raw zone is private `work/gis/raw/`. Each version has `normalized/`, `derived/`, and `published/` zones under `work/gis/<version>/`. Keep raw inputs immutable. Commit scripts, locks and small QA reports only; GIS binaries, generated tiles and raw OSM responses stay outside Git. Production uses separate private raw/normalized/derived storage and a versioned public bucket/CDN; set upload object keys from the manifest, verify hashes before switching the registry pointer, and preserve public bytes forever. Local static serving is the proof adapter, not a substitute for durable object storage.

`TX-DEM-2026-001` covers `[104.30, 21.05, 104.80, 21.55]` in explicitly documented longitude/latitude order. This operational coverage includes the smaller import AOI and its camera buffer; it is not a legal/administrative boundary. Nodes are sampled at 65 × 65 per tile, levels 0–4; the finest grid has about 50–54 m spacing from a 60 m normalized DSM. Resampling never creates additional source detail. The viewer has finite availability, six concurrent terrain requests, integrity checks, ellipsoid fallback, truthful source metadata and source attribution. Heights are ellipsoidal metres, not altitude above ground. The ramp is a visual encoding of DSM height, not aerial imagery or a hazard analysis.

Sources and rights evidence:

- [Copernicus AWS COG processing description](https://copernicus-dem-30m.s3.amazonaws.com/readme.html): GLO-30 public COG layout and point-grid alignment.
- [Copernicus product handbook](https://dataspace.copernicus.eu/sites/default/files/media/files/2024-06/geo1988-copernicusdem-spe-002_producthandbook_i5.0.pdf), section 1.2.1: horizontal WGS84-G1150 and vertical EGM2008. The product is a DSM including vegetation/structures.
- [Copernicus WorldDEM-30 licence](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/DEM/resources/license/License-COPDEM-30.pdf), articles 4–6: use/adaptation/distribution with required attribution and liability notice. Both notices are included in the manifest/viewer. Legal-review date remains unset; this records the published licence terms, not an external legal opinion.
- [PROJ NGA grid provenance](https://github.com/OSGeo/PROJ-data/blob/master/us_nga/us_nga_README.txt): public-domain 2.5-minute EGM2008 grid. [Vertical-grid formula](https://proj.org/en/stable/operations/transformations/vgridshift.html) explains the explicit multiplier.
- [OSM copyright](https://www.openstreetmap.org/copyright) and [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/): the separate road extract is available under ODbL with attribution. It is not merged into a proprietary road database.

The raw COG source hash is the source version because the AWS object does not provide a product edition identifier in the inspected metadata. Source acquisition years are not silently treated as a current field observation. The road snapshot date is its OSM database timestamp. A named road point such as OSM way 469902122 (“Đèo Phiêng Ban”) is a source comparison, not a surveyed control point.
