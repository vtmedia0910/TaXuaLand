Provider-neutral checkpoint only. No Vercel project has been created, linked or deployed by this milestone. Build trace/cold parser tests are local evidence, not cloud acceptance.

## Exact operator setup

- Dedicated LAND staging Vercel project, linked by owner to this repository; keep PR delivery and required checks. Do not deploy another product or reuse its environment.
- Framework Preset: Next.js. Root Directory: `apps/web`. Enable **Include source files outside of the Root Directory in the Build Step** in Settings → Build and Deployment → Root Directory. This is required for packages, services, workers and infra. See [Vercel monorepo setting](https://vercel.com/docs/monorepos/monorepo-faq).
- Node.js Version: **24.x**, also constrained in both root and web package.json. Install Command: `pnpm install --frozen-lockfile`. Build Command: `cd ../.. && pnpm build`. Output Directory: Next.js default; no custom output override. Do not duplicate packages into apps/web.
- Use a dedicated staging project production deployment for LAND_ENVIRONMENT=STAGING and a stable exact HTTPS SERVER_ORIGIN. Arbitrary PR previews stay PREVIEW, build/UI only. Do not inject staging write secrets into Preview. Production LAND requires a separate approved environment and separate credentials; this milestone does not authorize it.
- Stage runtime variables: `.env.example` storage contract plus runtime DATABASE_URL, DATABASE_ENDPOINT_MODE, DATABASE_POOL_MAX and optional DATABASE_CA_CERT from the managed DB guide. Never set owner/test/bootstrap credentials or NEXT_PUBLIC secrets. Use secret-manager injection, not tracked env files or command-line passwords.
- Preview: LAND_ENVIRONMENT=PREVIEW, LAND_PREVIEW_ENABLED=true, SERVER_ORIGIN equal to the exact trusted `https://<VERCEL_URL>` for that deployment, without DB or object-store credentials. VERCEL_ENV/VERCEL_URL come from the platform. No wildcard origins or request-header derivation. If the exact URL is not configured, startup deliberately refuses it. Preview supports static home/login UI only; database-backed pages/APIs intentionally have no authority and are not staging smoke evidence.

## Runtime packaging

Next outputFileTracingRoot is the repository root. The build traces the existing parser with Next's bundled Node File Trace, using Node 24's TypeScript stripping for analysis. Explicit includes on legacy upload and signed finalize routes retain the parser's precise source/dependency closure, including pnpm links. No new package, duplicated source tree or distributed worker is introduced. See [Vercel file tracing guidance](https://vercel.com/kb/guide/how-can-i-use-files-in-serverless-functions).

The root build validates client JavaScript syntax, restores pnpm directory-link entries from Node File Trace into the two route traces (Next's include glob omits directories), and reconstructs the parser in a fresh directory from its trace. It then executes a synthetic workbook through the same permission-restricted child and verifies scratch removal. Both affected route traces must include every parser dependency and exclude private work, env, Git and generated spatial assets. The parser resolves a traced monorepo root from the function cwd (or its two-level ancestor); LOCAL may explicitly set LAND_WORKSPACE_ROOT. Do not set a developer Windows path on Vercel. Verify actual deployed function layout before acceptance.

Node instrumentation awaits deployment configuration and the read-only DB authority gate before serving runtime requests; builds skip DB access, Preview validates configuration without connecting. Migration/provision/bootstrap are never invoked at startup. Node24 is required for the existing permission-restricted fork and native TypeScript execution. Serverless child-process compatibility still requires actual Vercel verification.

Workbooks are private object-backed and only downloaded to unique OS temporary scratch. No persistent volume, work directory, or apps/web/public/spatial is needed for STAGING/PRODUCTION persistence. Approved immutable CDN URLs resolve from PostGIS receipts; object storage is not a source of truth. Cesium assets remain generated by the existing prebuild copy, lazy loading and token-stripping remain unchanged. No Ion credential is added.
